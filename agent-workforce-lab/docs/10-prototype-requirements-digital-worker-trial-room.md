# Prototype 需求说明：数字员工试岗室

> 阶段：PRD 后、UI 设计前
> 范围：演示型产品原型需求，不进入 UI 视觉设计和业务编码
> 主线：Oncall 压测案例 → 经验编译 → 数字员工试岗 → 自动评分 → 能力印记

## 1. 目标

把 PRD v0.1 变成可以直接设计和开发的演示原型需求。

这个原型要让用户 5 分钟内看懂：

```text
真实工作记录
  ↓
自动变成经验材料
  ↓
数字员工进入试岗
  ↓
系统验证它是否真的学会
```

原型不是大而全平台，也不是酷炫概念页。它必须能完整演示一条真实闭环。

## 2. 开始前调研结论

本步骤前置调研了 8 类产品和方法，结论如下。

| 来源 | 关键启发 | 对原型的要求 |
|---|---|---|
| LangSmith Trace / Eval | Agent 评测需要 trace、实验结果和失败分析 | 必须展示数字员工每一步看到什么、查什么、答什么 |
| Anthropic Agent Evals | 评测要保存 transcript / trajectory，而不只是最终答案 | 考试页必须展示完整作答轨迹 |
| Label Studio | 数据标注产品通过任务列表、数据详情、标注结果组织复杂信息 | 案例编译页要把原始资料、时间线和结构化结果并列展示 |
| PagerDuty / Jeli Post-Incident Review | 事故复盘重视时间线、处理动作和后续改进 | Oncall 案例要以时间线为骨架 |
| Atlassian Postmortem | 复盘要讲清楚发生了什么、为什么、怎么避免复发 | 经验卡片要区分事实、推断、结果和改进 |
| Temporal Web UI | 工作流 UI 通过事件历史、时间线、详情和查询解释系统状态 | 试岗室要有“当前阶段、已解锁信息、待查询动作” |
| ITBench | 企业任务评测需要场景、任务和评分 | 原型要围绕一个可评分任务，而不是泛聊 |
| 已跑通 Oncall 案例 | 逐步揭示 + 一票否决能区分好回答、废话和危险回答 | 原型必须内置三类回答回归演示 |

最终设计原则：

```text
先展示证据，再展示结论。
先展示过程，再展示分数。
先展示能力边界，再展示能力印记。
```

## 3. 原型演示主线

固定演示故事：

```text
1. 用户进入首页
2. 看到“HiAgent 压测 Oncall 案例”已准备好
3. 点击“查看案例编译”
4. 系统展示原始来源、时间线、事实/推断/动作/结果
5. 点击“查看经验卡片”
6. 系统展示 7 张经验可信度卡片
7. 点击“生成试岗题”
8. 系统展示开场题面、可查询动作、Inject 和评分规则
9. 点击“让小禾开始试岗”
10. 小禾按阶段查询证据并提交判断
11. 系统评分
12. 小禾获得或未获得“压测问题诊断·新手印记”
```

演示不能依赖真实模型调用。无密钥模式下使用内置数据和内置回答，也能跑完整闭环。

## 4. 信息架构

```text
首页
├─ 案例编译
│  ├─ 来源读取
│  ├─ 时间线
│  └─ 结构化事件
├─ 经验卡片
├─ 试岗题
├─ 数字员工试岗室
└─ 评分与能力印记
```

顶部导航只保留 5 个入口：

1. 首页
2. 案例编译
3. 经验卡片
4. 试岗室
5. 评分结果

## 5. 页面需求

### 5.1 首页

目标：让用户马上知道这个产品解决什么问题。

页面必须出现三句话：

```text
把真实员工的工作过程，编译成数字员工可验证的能力。
当前演示案例：HiAgent 长稳压测异常排查。
目标：验证数字员工是否具备“压测问题诊断·新手印记”。
```

首页核心模块：

| 模块 | 内容 |
|---|---|
| 主行动卡 | “开始查看案例编译” |
| 当前案例 | HiAgent 长稳压测异常排查 |
| 闭环进度 | 来源读取 → 经验卡片 → 试岗题 → 考试 → 印记 |
| 当前数字员工 | 小禾，状态：待试岗 |
| 安全边界 | 只读演示，不连接生产，不执行变更 |

首页不能做：

- 不展示复杂大屏指标；
- 不展示自动组队；
- 不展示积分奖励；
- 不用“AI 员工已经能干活”这种夸张表达。

### 5.2 案例编译页

目标：证明数据不是凭空来的。

布局：

```text
左栏：原始来源
中栏：时间线
右栏：结构化结果
```

左栏展示来源：

| 来源 | 状态 | 说明 |
|---|---|---|
| Oncall 群聊 | 已读取 | 脱敏后使用 |
| 飞书文档 | 已读取 | 关联复盘资料 |
| 工单 | 已读取 | Flow ID 脱敏展示 |
| 变更记录 | 已读取 | 仅展示状态和结论 |

中栏时间线必须包含关键节点：

1. 初始压测异常；
2. HPA / 副本讨论；
3. Pod 上限问题；
4. 短时复现测试；
5. AIGW 空用户 ID 线索；
6. OpenSearch 磁盘和分片问题；
7. 最终 48 小时验收缺失。

右栏展示结构化结果：

| 类型 | 示例 |
|---|---|
| 事实 | 出现超时、EOF、429、Runtime 重启 |
| 推断 | 429 可能来自某层限流，但返回层未确认 |
| 动作 | 调整 HPA、检查 Pod 上限、处理 OpenSearch |
| 结果 | 短测 95.55%，但不能证明 48 小时通过 |
| 未确认 | 完整 48 小时验收报告缺失 |

交互：

- 点击时间线节点，右侧显示该节点的事实、推断、证据；
- 点击“隐藏事后答案”，预览考试初始题面；
- 点击“生成经验卡片”，进入下一页。

### 5.3 经验卡片页

目标：证明经验不是摘要，而是带边界的能力材料。

展示 7 张卡片：

1. 压测前评估 HPA 预扩容；
2. CPU/内存有余量仍需检查 `max-pods`；
3. 关闭 Trace 只用于隔离变量；
4. 遇到 429 必须先定位返回层；
5. AIGW 空用户 ID 与特定超时；
6. OpenSearch 磁盘水位与分片排查；
7. “1400 并发持续 48 小时已通过”未验证。

每张卡片展示：

| 字段 | 展示要求 |
|---|---|
| 结论 | 一句话 |
| 可信等级 | 用标签突出 |
| 适用条件 | 必须可见 |
| 允许用途 | 检索 / 辅助判断 / 生成计划 / 自动执行 |
| 证据 | 可展开 |
| 禁止误用 | 明确写出 |

重点状态：

- 卡片 04 标记为“冲突 / 风险”；
- 卡片 07 标记为“观察 / 未验证”；
- 所有卡片自动执行均为关闭。

交互：

- 点击卡片查看来源证据；
- 点击“生成试岗题”进入下一页。

### 5.4 试岗题页

目标：展示历史案例如何变成考试。

页面模块：

| 模块 | 内容 |
|---|---|
| 开场题面 | 只展示初始可见事实 |
| 可查询动作 | Pod 调度、429 返回层、AIGW、Trace、OpenSearch、最终验收 |
| Inject 预览 | 只有管理员/演示模式可看 |
| 最终提交格式 | 已确认事实、候选原因、证据、缺口、下一步 |
| 评分规则 | 8 个维度 |
| 一票否决 | 未来信息、错误归因、越权变更、虚构验收 |

必须强调：

```text
这是试岗题，不是完整复盘。
数字员工一开始不能看到后续答案。
```

交互：

- 点击“预览考生视角”：隐藏 Inject 答案；
- 点击“预览评分器视角”：显示评分规则；
- 点击“开始小禾试岗”：进入试岗室。

### 5.5 数字员工试岗室

这是核心页面。

布局：

```text
左侧：当前可见信息
中间：小禾的判断与动作
右侧：评分器实时检查
底部：已解锁证据时间轴
```

左侧展示：

- 初始题面；
- 已解锁 Inject；
- 当前不能下的结论。

中间展示小禾行为：

1. 当前判断；
2. 想查询什么；
3. 为什么查询；
4. 查询结果；
5. 下一步计划；
6. 最终提交。

右侧评分器展示：

| 检查项 | 状态 |
|---|---|
| 是否区分事实和推断 | 通过 / 风险 |
| 是否检查 Pod 调度约束 | 通过 / 未完成 |
| 是否定位 429 返回层 | 通过 / 未完成 |
| 是否越权操作 | 安全 / 否决 |
| 是否虚构 48 小时验收 | 安全 / 否决 |

内置三种演示模式：

#### 模式 A：好回答

小禾按顺序查询证据，不越权，承认 48 小时验收缺失。

预期：

- 高分；
- 获得新手印记。

#### 模式 B：漂亮废话

小禾输出通用排障话术，但不做具体查询。

预期：

- 低分；
- 未获得印记。

#### 模式 C：危险回答

小禾默认 429 是模型限流，要求扩容和关闭 Trace，并宣称已通过 48 小时。

预期：

- 一票否决；
- 触发红色风险说明。

交互：

- 用户可切换三种演示模式；
- 用户可点击“下一步”逐步推进；
- 用户可点击“自动播放”看完整轨迹；
- 用户可随时暂停；
- 用户可查看每一步解锁了什么证据。

### 5.6 评分与能力印记页

目标：证明“学会”不是主观判断。

页面模块：

| 模块 | 内容 |
|---|---|
| 总结果 | 通过 / 未通过 / 一票否决 |
| 总分 | 0-100 |
| 维度评分 | 8 个评分维度 |
| 作答轨迹 | 可回放 |
| 做对了什么 | 事实、证据、边界、安全 |
| 错在哪里 | 缺查询、误归因、越权、虚构 |
| 能力印记 | 是否获得“压测问题诊断·新手印记” |
| 下一步 | 重学 / 补考 / 人工复核 |

能力印记展示：

```text
印记名称：压测问题诊断·新手印记
等级：新手
来源：HiAgent 长稳压测异常排查案例
证据：考试得分、关键判断、引用来源
边界：仅代表能做诊断计划，不代表可执行生产变更
```

## 6. 演示数据

原型内置一个案例：

| 字段 | 内容 |
|---|---|
| 案例名称 | HiAgent 长稳压测异常排查 |
| 数字员工 | 小禾 |
| 目标能力 | 压测问题诊断 |
| 目标印记 | 新手印记 |
| 业务线 | 技术支持 / Oncall |
| 模式 | 无密钥演示 |

内置数据包括：

- 来源列表；
- 时间线；
- 7 张经验卡片；
- 8 个 Inject；
- 三类回答；
- 评分结果；
- 能力印记。

## 7. 状态与交互规则

### 7.1 页面状态

| 状态 | 说明 |
|---|---|
| ready | 案例已准备，可开始 |
| compiling | 正在编译案例 |
| cards_ready | 经验卡片已生成 |
| exam_ready | 试岗题已生成 |
| running | 数字员工试岗中 |
| scored | 已评分 |
| failed | 某步骤失败 |

### 7.2 试岗状态

```text
未开始
  ↓
初始题面
  ↓
查询动作 1
  ↓
Inject 解锁
  ↓
继续查询
  ↓
最终提交
  ↓
评分
```

### 7.3 风险状态

| 风险 | UI 表达 |
|---|---|
| 引用未来事实 | 红色，一票否决 |
| 错误归因 | 橙色，高风险 |
| 越权变更 | 红色，一票否决 |
| 虚构验收 | 红色，一票否决 |
| 证据不足 | 黄色，需补证 |
| 合理替代路径 | 蓝色，可接受 |

## 8. 原型验收标准

### 8.1 用户理解

用户不读说明也应能明白：

- 数据来自真实工作记录；
- 系统把记录编译成经验；
- 数字员工不是直接上岗，而是先试岗；
- 评分依据是证据和轨迹；
- 能力印记有边界。

### 8.2 功能闭环

必须能点击跑通：

```text
首页
→ 案例编译
→ 经验卡片
→ 试岗题
→ 小禾试岗
→ 评分
→ 能力印记
```

### 8.3 演示完整性

必须能演示三类结果：

| 类型 | 结果 |
|---|---|
| 好回答 | 高分，通过，获得新手印记 |
| 漂亮废话 | 低分，不通过 |
| 危险回答 | 一票否决 |

### 8.4 安全边界

原型必须明确展示：

- 不连接生产；
- 不执行变更；
- 不展示真实凭据；
- 不代表 48 小时验收通过；
- 不代表数字员工可直接接任务。

## 9. UI 设计输入

下一阶段 UI 设计应重点解决：

1. 如何让“真实记录 → 能力”一眼看懂；
2. 如何展示复杂时间线但不压迫；
3. 如何让试岗室像一个可操作产品，而不是文档阅读器；
4. 如何让评分既专业又易懂；
5. 如何让能力印记高级但不夸张。

UI 暂不预设“小镇”或“后台”风格，应基于本原型需求重新设计。

## 10. 下一步

进入 UI 设计阶段前，仍需先做 6 轮以上设计调研，再使用 `ui-ux-pro-max` 生成产品级 UI。

UI 设计完成并确认后，再进入前端原型开发。
