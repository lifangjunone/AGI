# 产品转向：用开源工作上下文底座构建“会工作的数字分身”

> 结论：暂停继续扩展“上传资料—宣布学会—考试—运营台”的旧路径。产品第一阶段改为建立真实员工的工作上下文，让数字分身从持续发生的工作中低负担学习。

## 一句话产品定义

**把真实员工散落在聊天、文档、会议和 AI 工具中的工作经历，持续整理成有来源、可验证、可调用的工作能力，让数字分身从辅助逐步成长为可独立工作的数字员工。**

## 为什么原来的方向不可用

旧路径把“考试、任务、运营”放在学习之前，却没有回答数字员工究竟如何学会真人的工作：

- 上传资料不等于掌握工作；
- 真人反复填表、聊天教学的成本太高；
- 只记录结论，无法学习判断过程、异常调整和能力边界；
- 系统宣布“已学会”没有证据，用户不会信任；
- UI 即使精美，也无法掩盖底层没有真实学习过程。

因此产品的正确顺序是：

```text
授权连接工作数据
        ↓
持续识别真实工作案例
        ↓
提炼事实、方法、判断、工具和边界
        ↓
在真实工作入口提供旁路辅助
        ↓
用实际结果验证掌握程度
        ↓
逐步获得更高的执行权限
```

## 第一产品形态：工作分身成长器

产品首先做成轻量桌面端，而不是先做任务运营后台。

用户每天只需要看到三件事：

1. **今天学了什么**：从哪些 Oncall、文档、会议或 AI 协作中形成了哪些新认识；
2. **现在能帮什么**：可以检索背景、准备回复、给出排查建议，还是能完成某个受限步骤；
3. **哪里还不会**：缺少什么证据、存在什么冲突、何时必须询问真人。

系统自动完成大部分整理，只在以下情况打扰真人：

- 两份来源互相冲突；
- 高风险操作需要授权；
- 关键判断缺少依据；
- 系统从结果中发现原有方法可能失效。

数字分身的成长不是“导入了多少知识”，而是权限逐级变化：

```text
可检索 → 可建议 → 可起草 → 可执行受限步骤 → 可独立完成低风险任务
```

考试和任务运营仍然保留，但后移到“已有足够真实工作证据”之后，作为能力校准和组织治理工具，不再充当学习本身。

| [Mirrai](https://github.com/Ch1rpys/Mirrai) | 多阶段蒸馏、自动记忆抽取、透明展示每轮引用的记忆、多渠道接入、本地存储 | “学到了什么、回答引用了什么”必须对用户透明 | 面向情感陪伴，不能复制其业务模型 |
| [awesome-persona-distill-skills](https://github.com/xixu-me/awesome-persona-distill-skills) | 汇总从资料提取决策框架、判断标准、工具习惯和表达模式的 Skill | 重点研究大师、老板、同事 Skill 与 Skill Fidelity Bench，补充工作判断蒸馏和保真评测 | 多数是静态 Skill，不具备持续采集、权限治理和真实工作闭环 |

## 整合原则：开源优先，不再自造底座

后续每项基础能力先查找并评估成熟开源实现：

- 数据连接与增量同步：优先复用 MyContext 的接口思想和可独立组件；
- 本地上下文、检索与证据链：优先适配成熟存储和检索模块；
- 人格与判断蒸馏：组合 digital-twin-skill、Second Me 和相关 persona skills 的方法；
- 隐私与脱敏：参考 WeClone 的数据处理链；
- 透明记忆：参考 Mirrai 的“本轮引用了哪些记忆”；
- 能力保真评估：研究 Skill Fidelity Bench，不再用资料数量或回答长度替代能力。

自研只保留真正差异化的部分：

1. 从工作记录重建“问题—判断—操作—结果—调整”；
2. 区分事实、方法、推断、边界与真人确认；
3. 用真实工作结果更新可信度；
4. 按风险和证据逐级放权；
5. 数字员工在任务中动态求助与协作。

## 工程整合方式

不直接把多个仓库拼接进现有代码，而是建立稳定的适配边界：

```text
飞书 / Oncall / AI 工具 / 本地文件
                ↓
        Source Connector API
                ↓
   Local Context Store + Evidence
                ↓
     Distillation / Retrieval API
                ↓
        Work Twin Runtime
                ↓
建议、草稿、受限执行、真实结果回流
```

每个开源组件都通过适配器接入，保留：

- 原项目、版本、许可证和修改记录；
- 数据来源、授权范围与撤回状态；
- 可替换接口，避免被单一项目绑定；
- 失败透明，不用演示数据伪装成功。

## 对当前项目的处理

### 立即暂停

- 继续美化旧首页和空运营台；
- 用手工填表伪装持续学习；
- 用固定规则宣布“已掌握能力”；
- 在缺少真实工作上下文时扩展积分、考试和任务广场。

### 保留但后移

- 数字员工身份；
- 能力准入与考试；
- 任务发布、动态求助和任务组；
- 独立评审、真人验收和证据回流。

### 下一步只做一条真实主线

以已经验证的 Oncall 压测案例为首条产品主线：

1. 授权连接 Oncall 群聊和关联飞书文档；
2. 增量采集并保留来源；
3. 自动重建处理案例；
4. 蒸馏排查方法、判断条件、失败尝试和升级边界；
5. 在下一次类似问题中先给真人旁路建议；
6. 对比真人最终处理结果，更新分身可信度。

跑通后再扩展到其他工作类型。

## 许可证结论

MyContext 使用 **Elastic License 2.0**：允许使用、修改和内部自托管，但禁止把其主要功能作为面向第三方的托管或管理服务提供。产品化前必须完成逐依赖许可证清单与法务评估。

其他项目也必须逐一核实仓库中的实际 License，不能因为 README 写“开源”就默认可以商业集成。

## 当前结论

本产品不再被定义为“数字员工考试运营台”，而是：

> **以个人工作上下文为底座，让数字分身持续学习真实工作，并用真实结果逐步获得能力和权限的工作分身平台。**

运营端仍然存在，但它管理的是组织授权、风险、能力证据和任务放权，不负责替用户手工教出一个数字员工。
