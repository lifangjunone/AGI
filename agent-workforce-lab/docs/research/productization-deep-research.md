# 从真实案例到数字员工产品：产品化深度调研

> 日期：2026-10-29
> 目的：回答已经跑通一个真实 Oncall 案例后，如何把方法孵化成长期可用产品，而不是继续制作案例 Demo。

## 结论

行业已经分别解决了采集、流程发现、Agent 构建、长期记忆和 Agent 评测的一部分，但公开资料中没有发现一款产品完整覆盖：

```text
低打扰读取真实工作
→ 还原人的判断过程
→ 形成可追溯经验
→ 数字员工持续学习
→ 用新任务证明能力
→ 按证据逐步放权
```

本产品不应该复制任一竞品的界面，而应该把这些能力组合成“数字员工孵化系统”。

## 六轮调研

### 1. 从真人示范学习：Lindy Watch and Learn

来源：

- <https://www.lindy.ai/product/watch-and-learn>

官方页面明确表达“真人示范一次，Agent 观察并学习”。它证明用户更愿意在正常工作中示范，而不是额外编写教程。

采用：

- 学习入口应是“从已有工作中学习”和“跟随一次工作”，不是空白知识库表单。
- 数字员工遇到无法解释的步骤时再提问。

不直接采用：

- 一次示范不能证明能力稳定。
- 学到流程不等于理解判断边界。

### 2. 从多条工作轨迹发现流程：UiPath Task Mining

来源：

- <https://docs.uipath.com/task-mining/automation-cloud/latest/user-guide/introduction>

官方文档说明 Task Mining 针对已知任务采集多个 trace，利用 AI 聚类相同页面与步骤，合并变化路径并生成决策点。

采用：

- 单个案例只产生候选经验；多次相似案例合并后才形成稳定模式。
- 产品核心对象应该是“工作轨迹”和“决策点”，不是聊天摘要。

不直接采用：

- 默认录制点击、键盘与截图侵入感过强，会诱发监控感和表演数据。
- 首选业务系统已经存在的聊天、工单、文档、变更和 Agent trace；桌面采集只能自愿、按任务开启。

### 3. 企业数字员工平台：StaffDeck

来源：

- <https://github.com/OpenBMB/StaffDeck/blob/main/README.zh.md>

官方 README 将数字员工定义为拥有岗位、工号、能力档案和工作记录的持续主体，并包含状态机 SOP、分层知识检索、Trace、真人接管和反馈分析。

采用：

- 数字员工必须是长期对象，具有版本、能力档案、工作记录和接管机制。
- 流程型经验需要结构化 SOP 和状态机，而不是只存 Prompt。
- 工作结果和反馈必须回到能力生命周期。

差异：

- 本产品首先解决“经验怎样自动产生、能力怎样被证明”，而不是首先提供 Agent 配置和运行平台。
- 不让用户手工搭建一个复杂数字员工后再开始积累经验。

### 4. 数字分身与长期身份：Second Me、WeClone、digital-twin-skill

来源：

- <https://github.com/mindverse/Second-Me>
- <https://github.com/xming521/WeClone/blob/master/README_zh.md>
- <https://github.com/FredHJC/digital-twin-skill>

这些项目证明聊天、文档和记忆可以形成长期身份、风格或个人上下文，也强调本地隐私、持续更新和多场景身份。

采用：

- 同一个数字员工应持续成长，而不是每次运行临时创建。
- 新数据进入后产生新版本，保留之前的能力状态与来源。
- 数据先脱敏，再编译；访问权限跟随来源。

不直接采用：

- 说话像某个人不等于会完成其工作。
- 微调或 Persona 相似度不是工作能力证明。
- 产品不冒充真人，不隐藏其数字员工身份。

### 5. Agent 模板与预制角色：Agency Agents

来源：

- <https://github.com/msitarzewski/agency-agents>

项目用角色描述、工作流、交付物和成功指标快速生成大量专用 Agent。

采用：

- 岗位目标、交付标准、沟通方式可以作为数字员工的起始骨架。
- Skill 可以作为能力发布格式之一。

反向结论：

- 预制 Prompt 只能说明“希望它怎样工作”，不能证明它真的会。
- 没有真实来源、考试和结果证据的角色不能进入可接任务状态。

### 6. Agent 评测与持续回归：Anthropic Agent Evals

来源：

- <https://www.anthropic.com/research/demystifying-evals-for-ai-agents>

官方文章区分 task、trial、grader、transcript/trace/trajectory、outcome 和 evaluation harness，并建议组合代码、模型和人工评分。真实失败可以转成初始评测集；能力评测成熟后应转为持续回归集。

采用：

- 每项能力都必须绑定任务集、完整轨迹、结果状态和评分器版本。
- 先用硬规则和结果校验，开放表达再用模型评分，少量人工用于校准。
- 一次通过只产生初级资格；多次新任务和真实结果才能升级。
- 生产失败和退回案例自动进入后续回归集。

不直接采用：

- 分数不是产品目标，可信放权才是。
- 不能用单一 LLM Judge 决定是否具备生产权限。

## 对产品的直接约束

1. 首页围绕“数字员工成长与工作结果”，不是案例演示步骤。
2. Oncall 是第一个能力模板，不是产品唯一内容。
3. 学习材料默认由系统从真实工作轨迹生成，真人不承担逐条教学。
4. 真人只处理冲突、高风险、低置信和放权决策。
5. 数字员工不能自称学会；能力来自独立试岗和真实结果。
6. 产品必须能接入第二个案例、第二位员工和第二项能力，才算产品化完成。
7. 任何预置数据都必须标记为样例，不能冒充真实运行。

## 对抗结论

### 如果只做案例编译器

用户会把它理解为复盘/知识库工具，看不到数字员工持续成长和接任务价值。

### 如果只做 Agent 创建器

产品会退化成 Prompt 管理器，无法回答为什么相信这个数字员工。

### 如果只做考试平台

考试和真实工作脱节，题库维护又回到专家人工负担。

### 如果直接做任务广场

没有可信能力档案，所谓自主接单只是模型自我声明。

### 如果要求专家逐条确认

产品会重复“养虾”类方案的人力失败；应采用例外审核、结果校准和抽样审计。
