# PRD 前置调研：数字分身学习与试岗系统

> 目的：在写 PRD v0.1 前，先核实业界做法与本项目已跑通的业务案例，明确第一版产品到底该做什么、不做什么。

## 一、结论

PRD v0.1 应聚焦一个闭环：

```text
真实工作记录
  ↓
自动提取事实、动作、判断、结果
  ↓
生成经验可信度卡片
  ↓
编译成逐步揭示的试岗案例
  ↓
数字员工考试作答
  ↓
自动评分与能力印记升级
```

第一版不应先做完整数字员工广场、自动组队、积分商城或复杂组织治理。原因是：产品最核心的不确定性不是“数字员工怎么展示”，而是**真实员工经验能不能低成本转成数字员工可学习、可验证的能力**。

本次 Oncall 压测案例已经证明这条主线可行，所以 PRD 应围绕“学习与试岗”展开。

## 二、6 轮以上调研摘要

### 第 1 轮：企业数字员工平台

参考：

- StaffDeck：https://github.com/OpenBMB/StaffDeck/blob/main/README.zh.md
- Sintra：https://www.sintra.ai/
- Relevance AI：https://relevanceai.com/

核实到的共性：

- 都强调“数字员工 / AI 员工 / 专家 Agent”。
- StaffDeck 明确提到把专业员工经验、流程和判断标准固化为数字员工，并支持能力档案、工作记录、权限隔离和发布复用。
- Relevance AI 强调企业 Agent 的 evaluation、monitoring、governance。
- Sintra 强调有岗位、身份和业务角色的 AI workers。

对本产品的启发：

- 数字员工必须有岗位、身份、能力档案和工作记录。
- 不能只做聊天机器人，必须让用户看到它“凭什么能做”。
- PRD v0.1 要先定义能力档案和试岗记录，而不是先做华丽首页。

不采用：

- 不直接照搬“买一个 AI 员工”式营销。
- 不把未验证能力包装成可交付能力。

### 第 2 轮：个人数字分身与人格克隆

参考：

- Second-Me：https://github.com/mindverse/Second-Me
- WeClone：https://github.com/xming521/WeClone/blob/master/README_zh.md
- digital-twin-skill：https://github.com/FredHJC/digital-twin-skill

核实到的共性：

- Second-Me 强调本地训练、记忆建模、隐私控制。
- WeClone 强调从聊天记录创建数字分身，支持聊天数据导出、预处理、模型训练、部署。
- digital-twin-skill 强调用聊天记录蒸馏说话风格，也支持飞书、微信、截图 OCR 等数据来源。

对本产品的启发：

- “像不像真人”不是企业工作场景的首要目标。
- 需要采集真实材料，但不能只学习语气和表达。
- 能力档案要区分：表达风格、知识事实、操作流程、判断标准、证据边界。

不采用：

- 不做人格克隆作为核心卖点。
- 不把“说话像专家”当作“会专家工作”。

### 第 3 轮：Watch-and-Learn / 示范式学习

参考：

- Lindy Watch and Learn：https://www.lindy.ai/product/watch-and-learn

核实到的能力：

- 用户可以录制自己做任务，或写下步骤。
- Agent 学会后可按需或定时执行。
- 产品表达重点是“show it once, it takes it from there”。

对本产品的启发：

- 教学不应要求专家长篇整理文档。
- 最好从真实工作过程、历史记录和少量示范中自动学习。
- PRD v0.1 要支持“从历史案例生成学习材料”，再允许少量人工补充。

不采用：

- 不要求专家每个流程都重新录屏示范。
- 不承诺“教一次就完全会”，必须经过考试和试岗。

### 第 4 轮：流程挖掘与任务挖掘

参考：

- UiPath Process Mining：https://docs.uipath.com/process-mining/automation-suite/2024.10/user-guide/introduction-to-process-mining
- Microsoft Process Advisor：https://learn.microsoft.com/en-us/power-automate/process-advisor-overview

核实到的能力：

- 流程挖掘把系统事件日志转成流程视图，发现瓶颈、偏差和根因。
- 任务挖掘关注人在桌面或系统中的操作过程。

对本产品的启发：

- 数据采集应优先走“已有系统记录”：群聊、工单、文档、变更、日志、复测结果。
- 桌面旁听/录屏不是第一优先级，因为成本高、隐私压力大、容易让人演戏。
- PRD v0.1 先做“工作记录编译器”，不要先做“员工监控采集器”。

不采用：

- 不自动扫描员工电脑。
- 不默认录屏、录键盘或抓窗口内容。

### 第 5 轮：Agent 评测与数据集

参考：

- Anthropic Agent Evals：https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents
- LangSmith Datasets：https://docs.smith.langchain.com/evaluation/how_to_guides/manage_datasets_in_application
- Ragas：https://docs.ragas.io/en/stable/
- OpenAI Evals：https://github.com/openai/evals

核实到的共性：

- Agent 评测不能只看最终答案，要看轨迹、工具调用、证据、失败模式。
- 数据集需要可复用、可回归。
- 评分需要结合规则、程序检查、模型判断和人工校准。

对本产品的启发：

- 数字员工考试不能只问“答案是什么”。
- 必须记录它看到了什么、查了什么、为什么这么判断、有没有越权。
- PRD v0.1 要有自动评分规则和一票否决项。

不采用：

- 不用模型裁判覆盖硬规则。
- 不把漂亮表达当作能力证明。

### 第 6 轮：AIOps / SRE 试岗基准

参考：

- IBM ITBench：https://github.com/IBM/ITBench
- Microsoft AIOpsLab：https://github.com/microsoft/AIOpsLab

核实到的能力：

- ITBench 面向复杂、真实启发的企业 IT 自动化任务。
- AIOpsLab 可部署微服务环境、注入故障、生成负载、导出遥测，并评估 Agent。

对本产品的启发：

- 真沙箱价值高，但第一版成本太大。
- 可以先用“逐步揭示的桌面推演”验证诊断判断、证据意识和安全边界。
- 真实执行能力放到后续“影子试岗”验证。

不采用：

- v0.1 不搭真实压测沙箱。
- 不要求生产镜像、生产依赖和故障注入环境。

### 第 7 轮：本项目真实 Oncall 实证

参考：

- 步骤 05：经验可信度卡片：https://bytedance.larkoffice.com/wiki/StXiwkXHtiWGadkY9X7c2anJnVO
- 步骤 06：历史 Oncall 自动生成可重演考试案例：https://bytedance.larkoffice.com/wiki/ENHZwdP9LiCwpvkdBy1cRJnqnYc
- 步骤 07：首个压测问题重演案例实测：https://bytedance.larkoffice.com/wiki/M4Y0w2opFiRAlykbItqc7VPBn2g

已经跑通：

- 从真实 Oncall 群聊、文档和变更记录提炼经验。
- 生成 7 张经验可信度卡片。
- 编译出一份压测问题重演考试。
- 设置逐步揭示信息，避免答案泄漏。
- 用规则区分好回答、漂亮废话和危险回答。

证明：

- 历史工作记录可以转成数字员工学习与试岗材料。
- 专家不需要逐条写题。
- 自动评分可以先覆盖关键风险。

还没证明：

- 数字员工能否在真实任务中持续稳定执行。
- 是否能跨多个业务域复用。
- 能力印记升级是否能长期准确。

## 三、PRD v0.1 应解决的问题

### 核心问题

企业里大量真实经验沉淀在群聊、飞书文档、工单、变更单和复测记录里，但这些经验没有进入组织能力系统。

结果是：

- 新人不知道专家当时怎么判断；
- AI 助手不知道某项工作真正怎么做；
- 专家不愿意额外写教程；
- 组织无法判断数字员工是否真的学会；
- 经验很容易随着项目结束、人员变化而丢失。

### 产品要解决

把真实工作记录自动编译成数字员工可学习、可考试、可追溯的能力材料。

### 一句话定位

**数字分身学习与试岗系统：把真实员工的历史工作过程，编译成数字员工可验证的能力。**

## 四、PRD v0.1 产品范围

### P0 必须做

1. 案例接入
   - 输入 Oncall 群、飞书文档、工单、变更链接。
   - 自动拉取可访问内容。
   - 脱敏凭据、个人敏感信息和客户敏感数据。

2. 事实整理
   - 拆分事实、推断、动作、结果、未确认项。
   - 保留来源链接。
   - 标记“当时可见”和“事后才知道”。

3. 经验可信度卡片
   - 结论、适用条件、证据、反例、缺失验证。
   - 可信等级：观察、有条件可信、已验证、稳定、冲突、已失效。
   - 允许用途：检索、辅助判断、生成计划、自动执行。

4. 试岗案例生成
   - 从历史案例生成逐步揭示题。
   - 初始题面不泄漏答案。
   - 查询动作触发 Inject。

5. 数字员工考试
   - 数字员工按阶段提交判断。
   - 记录作答轨迹、引用证据和下一步动作。

6. 自动评分
   - 规则评分。
   - 一票否决。
   - 区分正确判断、漂亮废话和危险回答。

7. 能力印记
   - 根据考试结果给出能力状态。
   - 不是一次通过就成为专家。
   - 能力必须带来源、证据和适用边界。

### P1 可后置

- 多案例能力聚合。
- 多数字员工对比考试。
- 影子试岗。
- 人工抽检工作台。
- 能力印记升级规则。
- 与任务发布系统联动。

### v0.1 不做

- 不做真实生产操作。
- 不做真实压测沙箱。
- 不做自动执行变更。
- 不做完整自动组队。
- 不做积分奖励体系。
- 不做员工桌面监控。
- 不做人格克隆。

## 五、PRD v0.1 页面建议

第一版页面不需要多，但必须让客户看懂闭环。

### 1. 案例导入页

用户输入：

- Oncall 群链接；
- 飞书文档链接；
- 工单链接；
- 变更链接；
- 可选补充说明。

用户看到：

- 读取了哪些来源；
- 哪些内容不可访问；
- 哪些敏感信息已脱敏；
- 是否可进入编译。

### 2. 经验编译页

用户看到：

- 时间线；
- 事实 / 推断 / 动作 / 结果；
- 来源证据；
- 事后结论是否被隔离。

### 3. 经验卡片页

用户看到每条经验：

- 结论；
- 可信等级；
- 适用条件；
- 支持证据；
- 反向证据；
- 允许用途。

### 4. 试岗案例页

用户看到：

- 开场题面；
- 可查询动作；
- Inject 列表；
- 答案泄漏检查；
- 评分规则。

### 5. 数字员工考试页

用户看到：

- 数字员工每一步看到的信息；
- 它做了什么查询；
- 它如何判断；
- 它引用了哪些证据；
- 是否触发风险。

### 6. 评分与能力印记页

用户看到：

- 总分；
- 一票否决项；
- 做对了什么；
- 错在哪里；
- 获得或未获得什么能力印记；
- 下一次需要补什么。

## 六、关键产品原则

1. 先验证能力，再允许接任务。
2. 先区分事实和推断，再生成结论。
3. 先看证据，再看表达。
4. 专家只处理冲突、高风险和低置信，不逐条确认。
5. 能力印记必须可回查来源。
6. 数字员工不能凭对话改变任务归属或执行生产动作。
7. 短测、阶段进展和最终验收必须分开。
8. 桌面旁听不是默认采集方式，避免监控感和演戏数据。

## 七、PRD 应采用的主线故事

建议固定使用已经跑通的 Oncall 压测案例做 PRD 主线：

```text
导入 Oncall 群和文档
  ↓
系统自动整理时间线
  ↓
抽取 7 张经验可信度卡片
  ↓
生成压测问题重演考试
  ↓
数字员工进入试岗室
  ↓
逐步查询证据并提交判断
  ↓
系统评分
  ↓
获得“压测问题诊断·新手印记”或失败重学
```

这样客户能理解：

- 数据从哪里来；
- 数字员工学了什么；
- 怎么证明不是瞎说；
- 为什么能减少专家工作量；
- 为什么现在还不能直接自动操作生产。

## 八、PRD 验收标准

PRD 写完后必须能回答：

1. 谁在用？
2. 输入什么？
3. 系统自动做什么？
4. 哪些地方需要人？
5. 数字员工学到了什么？
6. 怎么证明它学会了？
7. 怎么防止它胡说或越权？
8. 第一个真实案例怎么跑通？
9. 哪些能力明确不在 v0.1？
10. 下一阶段如何接任务发布和组队？
