# UI 设计前置调研与对抗评审：数字员工试岗室

> 阶段：UI 设计前
> 方法：多轮外部调研 + `ui-ux-pro-max` 设计系统检索 + 对抗评审
> 目标：为下一步产品级 UI 设计提供证据和约束，不直接进入编码

## 一、结论

下一版 UI 不能继续走“AI 概念首页 / 数字员工广场 / 大屏指标”的方向。

本产品最核心的可视化对象不是“员工形象”，而是：

```text
真实工作记录
  ↓
证据时间线
  ↓
经验卡片
  ↓
试岗轨迹
  ↓
评分证据
  ↓
能力印记
```

推荐方向：

> **可信工作台 + 试岗室。**

它应该像企业级评测工作台，而不是单纯聊天产品；像事故复盘和 Agent Eval 的结合，而不是普通后台表格。

视觉关键词：

- 企业可信；
- 高密度但不压迫；
- 证据优先；
- 过程可回放；
- 风险可解释；
- 能力边界清楚。

## 二、调研证据

### 1. Agent 评测产品：必须展示 trace / trajectory

来源：

- LangSmith Experiment / Trace：<https://docs.smith.langchain.com/evaluation/how_to_guides/analyze_an_experiment>
- Anthropic Agent Evals：<https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents>

调研发现：

- 成熟 Agent 评测不是只展示最终答案；
- 它会保存 trace / trajectory；
- 重点看输出、工具调用、中间结果、失败模式和评分标准。

对 UI 的约束：

- 数字员工试岗页必须展示“每一步看到了什么、查了什么、怎么判断”；
- 评分页必须能回放作答轨迹；
- 不能只给一个分数和一段总结。

### 2. 事故复盘产品：必须以时间线组织复杂事件

来源：

- PagerDuty / Jeli Post-Incident Review：<https://support.pagerduty.com/main/docs/postmortems>
- Atlassian Incident Postmortem：<https://www.atlassian.com/incident-management/postmortem>

调研发现：

- 事故复盘会围绕 timeline 展开；
- 重点是发生了什么、响应怎么处理、采取了什么解决步骤；
- 复盘不是为了展示“最终结论”，而是帮助后续避免类似问题。

对 UI 的约束：

- 案例编译页必须以时间线为主；
- 每个时间线节点要能展开事实、推断、动作、结果；
- “事后答案”和“当时可见信息”必须可视化区分。

### 3. 工作流可观测产品：必须能点击事件看详情

来源：

- Temporal Web UI：<https://docs.temporal.io/web-ui>

调研发现：

- 工作流 UI 通常有 History / Timeline；
- 点击事件可以看到详情；
- 支持不同视角，例如 Timeline、All、Compact、JSON。

对 UI 的约束：

- 试岗室需要“当前阶段 / 已解锁信息 / 事件详情”；
- 复杂数据不应该一次性全展开；
- 可以提供“考生视角”和“评分器视角”。

### 4. 标注产品：必须把原始数据、标注结果和机器建议并列

来源：

- Label Studio：<https://labelstud.io/guide/>

调研发现：

- 标注类产品处理复杂材料时，会把原始数据、标注对象、模型预标注和人工结果组合起来；
- 它不是一页讲故事，而是让用户检查和修正结构化结果。

对 UI 的约束：

- 案例编译页应使用三栏结构：

```text
原始来源｜时间线｜结构化结果
```

- 用户需要能看到系统为什么这样抽取；
- 不能只展示“已生成 7 张卡片”。

### 5. 企业任务基准：必须围绕可评分场景

来源：

- IBM ITBench：<https://github.com/IBM/ITBench>
- Microsoft AIOpsLab：<https://github.com/microsoft/AIOpsLab>
- OpenAI Evals：<https://github.com/openai/evals>

调研发现：

- 企业任务评测需要 scenario、problem、agent、trace、score；
- 好的 eval 往往来自真实 workflow；
- 没有 eval，很难判断模型或 Agent 改动是否真的有效。

对 UI 的约束：

- 原型必须围绕“HiAgent 长稳压测异常排查”这一个可评分任务；
- 首页不要展示过多未来模块；
- 试岗结果必须能区分好回答、漂亮废话和危险回答。

### 6. `ui-ux-pro-max` 设计系统检索

检索查询：

```text
enterprise AI agent evaluation workflow dashboard
```

设计系统建议：

| 项 | 建议 |
|---|---|
| 模式 | Enterprise Gateway / 企业可信入口 |
| 风格 | Minimalism & Swiss Style |
| 色彩 | 信任深蓝 + 绿色行动色 + 浅灰背景 |
| 字体 | Lexend / Source Sans 3 |
| 密度 | 8/10，高密度工作台 |
| 动效 | 5/10，标准动效，避免花哨 |
| 反模式 | 混乱登录流、弱审计轨迹、隐藏授权 |

采用理由：

- 产品面向企业内部原型，不适合过度娱乐化；
- 用户需要快速理解证据、状态和风险；
- 高密度工作台更适合时间线、卡片、评分和轨迹。

不采用：

- 大面积营销落地页；
- 过度 3D / 小镇地图；
- 像素风；
- 纯聊天界面；
- 游戏化积分视觉。

### 7. `ui-ux-pro-max` UX 规则检索

已命中的规则：

| 查询 | 命中规则 | UI 约束 |
|---|---|---|
| `stepper progress disclosure` | 多步流程要展示进度 | 全局闭环必须有 stepper |
| `error summary validation` | 错误摘要要可聚焦、可链接到字段 | 风险/否决项必须集中展示并可跳转 |
| `tab keyboard navigation` | 完整键盘导航、可见焦点 | 试岗室所有操作必须键盘可达 |
| `card status badge` | 状态徽章变化需可读、不可只靠颜色 | 卡片等级、风险状态必须有文本 |
| `process funnel stage` | 多阶段流程可用 funnel / process map，但要提供线性备选 | 闭环进度可以图形化，但必须有列表备选 |
| `dashboard evaluation score evidence` | 多指标评分适合 Bullet Chart | 评分页使用 bullet/progress，而不是大仪表盘 |
| `focus not obscured` | 固定导航不能遮挡焦点 | 顶栏和底部操作栏要预留滚动间距 |

未命中但已按规则处理：

- `timeline evidence workflow` 未命中；
- `state machine workflow` 未命中；
- 因此时间线采用外部产品证据 + 通用 UX 原则，不伪装成 skill 命中结果。

## 三、推荐 UI 架构

### 1. 全局导航

建议 5 个主入口：

```text
首页｜案例编译｜经验卡片｜试岗室｜评分结果
```

每个入口对应演示闭环的一个阶段。

顶部始终显示：

- 当前案例：HiAgent 长稳压测异常排查；
- 当前数字员工：小禾；
- 当前阶段：案例编译 / 试岗中 / 已评分；
- 安全状态：只读演示，不连接生产。

### 2. 首页

首页不是营销页，而是“演示控制台”。

核心布局：

```text
左：一句话价值 + 当前案例 + 主按钮
右：闭环进度 stepper
下：三张证明卡
```

三张证明卡：

1. 数据来自真实工作记录；
2. 经验带证据和边界；
3. 数字员工先试岗再获得能力印记。

### 3. 案例编译页

推荐三栏：

```text
来源列表｜时间线｜结构化抽取
```

关键交互：

- 点击时间线节点；
- 右侧显示事实、推断、动作、结果；
- 可切换“当时可见 / 事后结论”；
- 可一键预览考试初始题面。

### 4. 经验卡片页

推荐卡片网格 + 右侧详情。

卡片必须突出：

- 可信等级；
- 允许用途；
- 禁止误用；
- 来源证据。

状态标签必须使用文字，不只靠颜色。

### 5. 试岗题页

推荐分为两种视角：

| 视角 | 看到什么 |
|---|---|
| 考生视角 | 开场题面、可查询动作、最终提交格式 |
| 评分器视角 | Inject、评分规则、一票否决、证据索引 |

这样能让客户理解：数字员工不是“看完复盘答题”，而是在有限信息下逐步判断。

### 6. 数字员工试岗室

这是核心页面。

推荐四区布局：

```text
左侧：当前可见信息
中间：小禾的判断与动作
右侧：实时评分器
底部：已解锁证据时间轴
```

必要功能：

- 下一步；
- 自动播放；
- 暂停；
- 切换好回答 / 漂亮废话 / 危险回答；
- 点击证据回看来源；
- 风险触发时集中展示。

### 7. 评分与能力印记页

推荐结构：

```text
顶部：通过 / 未通过 / 一票否决
左：评分维度 bullet chart
中：关键作答轨迹回放
右：能力印记卡
底部：下一步建议
```

能力印记必须写清楚：

- 只代表诊断计划能力；
- 不代表可执行生产变更；
- 不代表 48 小时压测已经通过；
- 不代表可以直接接任务。

## 四、对抗评审

### 对抗问题 1：如果做成“数字员工广场”，会怎样？

失败点：

- 用户会以为重点是角色和空间；
- 真实证据、时间线、评分会被弱化；
- 很难解释“为什么它真的学会了”。

结论：

> v0.1 不适合广场作为主界面。广场可以作为未来任务协作阶段入口，但不是学习与试岗阶段的核心。

### 对抗问题 2：如果做成普通后台表格，会怎样？

失败点：

- 产品故事弱；
- 客户难以理解数字员工学习过程；
- 试岗过程不直观；
- 演示没有记忆点。

结论：

> 不能只做 CRUD 后台。必须有“试岗室”这一强产品场景。

### 对抗问题 3：如果做成聊天界面，会怎样？

失败点：

- 容易变成普通 AI 助手；
- 评分依据不清楚；
- 证据和时序容易丢；
- 用户难判断能力是否真实。

结论：

> 聊天只能作为小禾表达方式之一，不能作为主产品结构。

### 对抗问题 4：如果首页先强调 AI 自动干活，会怎样？

失败点：

- 与 v0.1 范围冲突；
- 容易让客户误解系统能执行生产变更；
- 安全边界不清楚。

结论：

> 首页必须强调“先试岗再接任务”，不能强调“立即自动执行”。

### 对抗问题 5：如果评分只显示总分，会怎样？

失败点：

- 不能解释为什么通过；
- 不能暴露危险回答；
- 无法形成可信能力印记。

结论：

> 评分必须拆成维度、轨迹、否决项和证据，不只展示总分。

### 对抗问题 6：如果只用红黄绿颜色表示风险，会怎样？

失败点：

- 可访问性差；
- 色弱用户难判断；
- 状态含义不明确。

结论：

> 风险状态必须用文字 + 图标 + 颜色三重表达。

### 对抗问题 7：如果移动端强行缩小四栏试岗室，会怎样？

失败点：

- 信息不可读；
- 操作难度高；
- 时间线和评分器互相挤压。

结论：

> 移动端不缩小桌面四栏，而是切换为分段面板：当前信息、动作、评分、证据。

## 五、设计系统建议

### 1. 色彩

采用 `ui-ux-pro-max` 推荐的企业可信色系：

| Token | 色值 | 用途 |
|---|---|---|
| Primary | `#1E3A5F` | 顶栏、主导航、关键标题 |
| Secondary | `#2563EB` | 链接、可操作信息 |
| Accent | `#16A34A` | 通过、开始、确认 |
| Background | `#F8FAFC` | 页面背景 |
| Foreground | `#0F172A` | 主文本 |
| Card | `#FFFFFF` | 卡片 |
| Muted | `#E9EEF5` | 分隔和弱背景 |
| Border | `#CBD5E1` | 边框 |
| Destructive | `#DC2626` | 一票否决、危险回答 |

补充状态色：

| 状态 | 建议 |
|---|---|
| 观察 | 灰蓝 |
| 有条件可信 | 蓝 |
| 已验证 | 绿 |
| 冲突 | 橙 |
| 一票否决 | 红 |
| 待人工复核 | 紫 |

### 2. 字体

建议：

- 标题：Lexend；
- 正文：Source Sans 3；
- 代码/证据 ID：等宽字体。

原因：

- Lexend 可读性好，适合企业产品；
- Source Sans 3 适合高密度信息；
- 证据 ID、Flow ID、节点 ID 用等宽字体更清晰。

### 3. 密度

采用高密度工作台，但保留关键留白。

建议：

- 桌面端最大信息密度；
- 1024 宽度变成双栏；
- 768 / 375 使用分段面板；
- 不允许横向滚动。

### 4. 动效

动效只表达三件事：

1. 证据被解锁；
2. 风险被触发；
3. 评分状态变化。

不做：

- 大面积粒子；
- 角色走动；
- 地图漫游；
- 无意义 loading 动画。

必须支持：

- 暂停自动播放；
- 减少动态效果；
- 键盘操作。

## 六、响应式策略

### 桌面 1440×900

使用完整四区试岗室：

```text
当前信息｜小禾动作｜评分器
底部证据时间轴
```

### 平板 1024×768

使用双栏：

```text
左：当前信息 + 证据
右：动作 + 评分
```

### 竖屏 768×1024

使用 tabs：

```text
信息｜动作｜评分｜证据
```

### 手机 375×812

使用分段卡片：

```text
顶部：阶段 + 安全状态
主体：当前面板
底部：下一步 / 暂停 / 查看评分
```

手机端不强行展示复杂时间线图，改为线性事件列表。

## 八、进入 UI 设计的判断

可以进入下一步 UI 设计，但必须遵守：

- 以“可信工作台 + 试岗室”为主方向；
- 不先做广场；
- 不先做小镇；
- 不先做聊天页；
- 不先做大屏；
- 每个页面都要能回答：证据在哪里、过程在哪里、评分依据在哪里、能力边界在哪里。
