# 自动化闸门、风险和指标

## 1. 为什么需要闸门

全自动化的可靠性不来自“更聪明的代理”，而来自每一步都有可判定的契约。代理可以生成代码和解释失败，但不能自行宣布生产变更安全。

闸门输出必须是：

- `PASS`
- `FAIL`
- `UNKNOWN`
- `WAIVED`（带审批人、原因和过期时间）

生产链路中 `UNKNOWN` 默认等同 `FAIL`。

## 2. 闸门矩阵

| 阶段 | 必需闸门 | 通过证据 | 失败动作 |
|---|---|---|---|
| 需求 | 完整性、无关键歧义 | schema 报告、澄清记录 | 停止并提问 |
| 规格 | 验收可测试、追踪完整 | spec lint、trace matrix | 修订规格 |
| 计划 | 风险、测试、迁移、回滚齐全 | plan policy report | 重做计划/审批 |
| 编码 | 范围受控、无违规修改 | diff policy | 拒绝变更 |
| 本地验证 | format/lint/type/test/build | 命令退出码、报告 | 代理有界修复 |
| PR | 必需检查、审查、分支保护 | GitHub Checks/Review | 禁止合并 |
| 制品 | 扫描、SBOM、签名、provenance | digest 和验证报告 | 禁止发布 |
| Staging | 健康、冒烟、迁移、契约 | 部署和测试事件 | 回滚 |
| Canary | SLO 和业务指标 | 指标窗口结果 | 自动中止/回滚 |
| Production | 稳定窗口 | 合成探测、告警、业务指标 | 回滚/事故 |

## 3. 风险评分

建议先使用规则评分，不让模型直接决定：

| 因素 | 示例加分 |
|---|---:|
| 文档/注释且无运行影响 | 0 |
| 低影响 UI 或内部逻辑 | 1 |
| 公共 API 行为改变 | 3 |
| 数据库 schema/数据迁移 | 4 |
| 认证、授权、支付、隐私 | 5 |
| IaC、网络、生产权限 | 5 |
| 不可逆或难回滚 | 5 |
| 跨多个服务/仓库 | 2 |
| 缺少对应自动测试 | 3 |
| 超过变更行数/文件阈值 | 2 |

示例分级：

- `0-2`：low
- `3-6`：medium
- `7-10`：high
- `>=11`：critical

模型可以补充风险说明，但只能提高风险或请求复核，不能降低规则算出的等级。

## 4. 自动化策略示例

| 风险 | 合并 | Staging | Production |
|---|---|---|---|
| Low | 全部检查通过后自动 | 自动 | 金丝雀指标通过后自动 |
| Medium | 1 名 CODEOWNER | 自动 | 1 名发布责任人或时间窗策略 |
| High | 领域 + 安全审批 | 自动但加强测试 | 人工批准 + 金丝雀 |
| Critical | 多方审批 | 隔离验证 | 变更窗口、双人授权、演练回滚 |

以下变更第一版一律不自动上生产：

- 破坏性数据库迁移
- 权限边界扩大
- 密钥和身份系统改变
- 支付、资金和高敏隐私逻辑
- 无法自动回滚的基础设施变更
- 监控或发布指标缺失

## 5. 测试策略

### 需求覆盖

每条验收条件至少关联一个自动化测试或一个明确的人工验证项：

```text
REQ-17
  -> SPEC-auth-03
  -> TASK-42
  -> src/auth/session.ts
  -> TEST-session-expiry-01
  -> BUILD sha256:...
  -> DEPLOY prod-20260814-01
  -> SLO auth_success_rate
```

### 测试金字塔

- 单元测试：业务规则和边界值
- 组件/集成：数据库、队列、缓存和外部适配器
- 契约测试：服务和客户端兼容
- E2E：少量核心用户旅程
- 合成探测：发布后持续验证
- 混沌/恢复：关键系统定期演练

### 防止无效测试

- 新测试应在旧版本失败或证明新增覆盖。
- Mutation testing 可用于高风险核心逻辑。
- 对改动行统计 diff coverage。
- 检测被跳过、删除或放宽断言的测试。
- flaky test 单独管理，不得无限自动重跑掩盖失败。

## 6. 发布 SLO

每个服务至少定义：

- 可用性
- 错误率
- 延迟 P50/P95/P99
- 饱和度
- 一个关键业务成功指标

金丝雀分析示例：

```text
成功条件（连续 10 分钟）：
- HTTP 5xx < 1%
- P95 latency 增幅 < 20%
- 核心业务成功率下降 < 2%
- 无新的 P1/P2 告警

失败条件：
- 任一硬阈值连续 3 个窗口失败
- 指标数据缺失超过 2 个窗口
- 数据完整性检查失败一次
```

## 7. DORA 指标

按照 DORA 当前五项软件交付指标记录：

| 维度 | 指标 | OneOPC 数据来源 |
|---|---|---|
| 吞吐 | Change lead time | commit 到生产成功事件 |
| 吞吐 | Deployment frequency | 生产部署事件 |
| 吞吐 | Failed deployment recovery time | 失败到恢复事件 |
| 不稳定性 | Change fail rate | 需要回滚/热修的部署比例 |
| 不稳定性 | Deployment rework rate | 为修复生产问题产生的非计划部署比例 |

指标用于改进系统，不用于比较不同上下文的个人或团队。

## 8. OneOPC 自身指标

### 流程

- 需求到规格时间
- 澄清率和平均澄清轮次
- 规格到首个 PR 时间
- 各阶段等待时间和执行时间
- 首次通过率
- 自动化完成率
- 人工升级率

### 代理

- 每任务尝试次数
- Token/费用/墙钟时间
- 代理修改后 CI 通过率
- 人工返工比例
- 无关变更比例
- 代理引入缺陷率

### 可靠性

- 工作流恢复成功率
- Webhook 重复/丢失率
- 沙箱启动失败率
- 错误分类准确率
- 回滚成功率和耗时

### 安全

- 未签名制品阻断数
- Secret 泄漏阻断数
- 高危漏洞豁免数量和过期数量
- 越权工具调用阻断数
- 非法状态转换阻断数

## 9. AI 功能评估

除了普通测试，还需维护固定评估集：

- 清晰需求
- 有意缺失关键字段的需求
- 冲突需求
- 恶意提示注入文档
- 跨模块变更
- 数据迁移
- 需要回滚的故障版本

评估：

- 规格完整性和事实一致性
- 是否在关键歧义处停止
- 任务拆分质量
- 代码正确性
- 测试有效性
- 安全边界遵守
- 成本和时延

模型或提示升级前必须回归评估，不以少量演示成功作为上线依据。

## 10. 豁免规则

任何闸门豁免必须包含：

- 被豁免的规则
- 风险说明
- 业务理由
- 补偿措施
- 审批人
- 生效范围
- 过期时间
- 后续任务

不允许永久、匿名、全局豁免。过期后自动恢复阻断。
