# 业界项目与最佳实践调研

## 1. 结论先行

“需求文档到上线”不是一个模型调用，而是一条跨越产品、研发、安全、交付和运行的受控状态机。当前方案可以分为四类：

1. **规格驱动工具**：解决“到底要做什么”。
2. **软件工程代理**：解决“如何产生候选代码变更”。
3. **CI/CD 与 GitOps 平台**：解决“如何确定性验证和部署”。
4. **平台工程与治理工具**：解决“如何规模化、审计和持续改进”。

任何只覆盖其中一类却宣称“全自动交付”的项目，都缺少生产闭环所需的关键能力。

## 2. 重点项目对比

### 2.1 规格与需求层

| 项目 | 核心能力 | 优点 | 局限 | OneOPC 用法 |
|---|---|---|---|---|
| GitHub Spec Kit | Constitution、Specify、Plan、Tasks、Implement | 结构完整，强调规格驱动开发 | 更像方法和模板，不负责部署闭环 | 参考其阶段模型和项目原则 |
| OpenSpec | Proposal、Design、Tasks、Spec Delta | 轻量、适合存量项目、规格与代码同仓 | 不负责编码质量和发布 | 第一版规格层首选 |
| Backstage Software Templates | 基于模板创建仓库、组件和基础设施 | 标准化“黄金路径”，适合多团队 | 平台本身较重，不是编码代理 | 第二阶段作为服务入口 |

**可复用实践：**

- 需求必须转换成结构化规格，而不是直接丢给编码代理。
- 每条需求都要有稳定 ID、验收条件、非功能约束和可追踪关系。
- 规格变更使用差异形式表达，审查“意图变化”而不只审查代码差异。
- 需求不完整时流程应进入 `NEEDS_CLARIFICATION`，禁止代理自行猜测关键业务规则。

### 2.2 编码代理层

| 项目 | 核心能力 | 优点 | 局限 | OneOPC 用法 |
|---|---|---|---|---|
| OpenHands | 本地/云端软件代理、终端、编辑器、工具和沙箱 | 通用性强、可本地运行、生态活跃 | 结果依赖模型和上下文，不能替代质量闸门 | 默认候选执行器 |
| SWE-agent | 针对 GitHub Issue 的软件工程代理 | 研究基础清晰，适合 issue-to-patch | 更偏问题修复，不覆盖完整产品流程 | 作为基准和备选执行器 |
| AWS sample-autonomous-cloud-coding-agents | 云端隔离编码代理与 GitHub 工作流样例 | 展示代理、PR、部署权限的组合方式 | 样例性质，绑定 AWS 组件 | 借鉴隔离和审批设计 |
| MetaGPT / ChatDev | 多角色模拟软件团队 | 适合研究角色分工和文档生成 | 角色对话不等于工程可验证性 | 不作为生产主链路 |

**可复用实践：**

- 每个任务在一次性沙箱或临时工作树中执行。
- 代理只获得完成任务所需的工具和最小权限。
- 代理必须运行项目原生测试，并把命令、输出摘要、变更和失败原因结构化保存。
- 代理只能创建候选分支/PR，不能直接写生产环境。
- 失败应分类为：规格不足、环境失败、测试失败、权限失败、模型无法完成。

### 2.3 CI、制品与供应链

| 项目/标准 | 核心能力 | OneOPC 应采用的实践 |
|---|---|---|
| GitHub Actions | PR 检查、构建、发布、环境保护、OIDC | 工作流即代码；最小 `GITHUB_TOKEN` 权限；生产用 Environment |
| SLSA | 软件供应链完整性等级和来源证明 | 生成 provenance，验证制品来自受信任工作流和提交 |
| Sigstore / Cosign | 无密钥签名、制品验证 | 对容器和发布制品签名，部署前验证 |
| Syft / CycloneDX | SBOM 生成 | 每个发布制品附带依赖清单 |
| Trivy / Grype | 镜像、依赖和配置扫描 | 阻断已知高危漏洞，允许有时限的显式豁免 |
| Semgrep / CodeQL | 静态分析 | PR 阶段运行；高风险路径提高规则强度 |

**可复用实践：**

- 合并前必须通过确定性 CI，不能以“代理自评通过”替代。
- 一次构建，产出不可变制品摘要；测试、预发布、生产使用同一摘要。
- 发布身份使用 OIDC 短期凭证，不保存长期云密钥。
- 第三方 Actions 固定到完整 commit SHA，并自动更新。
- 制品携带 SBOM、签名、来源证明和测试报告。

### 2.4 CD、渐进交付与运行闭环

| 项目 | 核心能力 | OneOPC 用法 |
|---|---|---|
| Argo CD | Git 作为期望状态、自动同步、自愈和审计 | Kubernetes 目标环境的 CD 控制器 |
| Argo Rollouts | 蓝绿、金丝雀、指标分析 | 生产渐进发布和自动回滚 |
| Flagger | 基于指标的渐进发布控制器 | 与 Argo Rollouts 二选一 |
| OpenFeature + Unleash/Flagsmith | 标准化功能开关 | 代码部署与功能曝光解耦 |
| OpenTelemetry | 日志、指标、追踪统一采集 | 为发布验证和事故定位提供数据 |
| Prometheus + Grafana | 指标存储、告警和可视化 | 本地 POC 的健康判断与看板 |
| OPA/Conftest、Kyverno | 策略即代码 | 校验 IaC、Kubernetes 和发布策略 |

**可复用实践：**

- CI 只更新 Git 中的期望版本，不直接持有集群管理员权限。
- 发布按 `dev -> staging -> canary -> production` 晋升。
- 每一阶段有时间窗、成功指标、失败阈值和自动回滚动作。
- 数据库迁移采用向后兼容的 expand/migrate/contract 模式。
- 发布事件自动关联提交、需求、制品摘要、配置版本和观测结果。

## 3. 单项目能覆盖多少

| 能力 | Spec Kit / OpenSpec | OpenHands / SWE-agent | GitHub Actions | Argo CD / Rollouts |
|---|---:|---:|---:|---:|
| 解析需求 | 强 | 弱 | 无 | 无 |
| 规格和任务 | 强 | 中 | 无 | 无 |
| 修改代码 | 弱 | 强 | 弱 | 无 |
| 自动测试 | 弱 | 中 | 强 | 弱 |
| 安全与供应链 | 无 | 弱 | 强 | 中 |
| 环境部署 | 无 | 弱 | 中 | 强 |
| 渐进发布 | 无 | 无 | 中 | 强 |
| 运行观测 | 无 | 弱 | 中 | 中 |
| 端到端审计 | 弱 | 中 | 中 | 中 |

因此 OneOPC 的价值不应是再造所有工具，而应是：

1. 定义统一的交付状态机和证据模型。
2. 编排现有工具，并对输入输出做契约校验。
3. 给每个闸门提供真实状态、日志和可回放记录。
4. 在失败时把任务路由到正确的修复主体。

## 4. 不建议作为第一版主线的方案

### 4.1 “多角色代理公司”

大量角色对话会增加 Token、时延和不确定性。只有当角色拥有不同工具、权限或独立验证责任时，拆分代理才有意义。

### 4.2 代理直接操作生产

模型输出不具备确定性，也容易受到提示注入和工具污染。生产写权限必须位于策略控制和部署控制器之后。

### 4.3 从需求直接生成代码

跳过规格澄清会把歧义推迟到最昂贵的阶段。先生成可审查的验收条件，再生成实现计划和代码。

### 4.4 只检查“测试是否绿色”

绿色测试只能证明已有检查通过，不能证明需求正确。必须同时检查需求覆盖率、变更风险、安全、迁移、可观测性和回滚能力。

## 5. 推荐组合

### POC

`Markdown/PDF 输入 -> OpenSpec -> OneOPC 状态机 -> 编码代理 -> GitHub PR -> GitHub Actions -> Docker Compose/kind -> Argo CD -> Prometheus`

### 团队级

在 POC 上增加：

- Backstage 服务目录和黄金路径
- Argo Rollouts 与功能开关
- OIDC、Cosign、SBOM、SLSA provenance
- 集中策略、审计、成本和 DORA 数据
- 多仓库依赖图与变更影响分析

### 企业级

再增加：

- 组织级身份和权限边界
- 独立构建平台与受控 Runner
- 合规证据存档、双人审批和职责分离
- 多集群、多区域、灾备演练和变更冻结策略
- 模型、提示、工具、数据访问的版本化治理
