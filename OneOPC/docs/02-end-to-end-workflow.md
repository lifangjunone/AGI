# 从需求文档到上线的 24 步流程

## 流程总览

```text
输入
  -> 需求摄取
  -> 规格澄清
  -> 风险与影响分析
  -> 计划和任务
  -> 隔离编码
  -> 本地验证
  -> PR 与 CI
  -> 制品和证明
  -> 环境部署
  -> 渐进发布
  -> 观测与回滚
  -> 反馈和复盘
```

每一步都必须定义五个元素：

- 输入契约
- 执行器
- 输出制品
- 通过条件
- 失败后的状态和责任人

## 阶段 0：平台准备

### 1. 注册项目

**输入：** 仓库地址、默认分支、技术栈、所有者、数据等级、部署目标。

**自动动作：**

- 检测构建工具、测试命令、Docker/IaC、代码所有者和 CI 配置。
- 创建项目清单和能力画像。
- 检查仓库保护、权限和必需 Secrets/OIDC 配置。

**输出：** `project.yaml`、项目能力报告、缺失项列表。

**闸门：** 所有者明确；代码可检出；至少有一个确定性验证命令。

### 2. 建立基线

**自动动作：**

- 在未修改代码的情况下运行构建、测试、扫描。
- 记录已有失败、覆盖率、性能和安全债务。
- 生成可复现的本地开发环境。

**输出：** baseline 报告。

**闸门：** 新任务只对“新增失败”负责，既有失败需显式登记，不能被代理悄悄忽略。

## 阶段 1：需求摄取与规格化

### 3. 摄取原始需求

**输入：** Markdown、DOCX、PDF、Issue、表单或 API。

**自动动作：**

- 保存原文件和内容哈希，禁止覆盖。
- 提取正文、表格、附件和来源元数据。
- 为需求生成稳定 ID。

**输出：** 原始输入快照、标准化文本。

**目录边界：**

```text
inputs/requirements/<requirement-id>/  # 原始输入，只读
work/<run-id>/                         # 研发过程资产
```

原始资料与 AI 生成物必须物理隔离。

### 4. 结构化需求

将自然语言转为：

- 背景与目标
- 用户和场景
- 范围内/范围外
- 功能需求
- 非功能需求
- 约束与依赖
- 验收条件
- 未决问题

**输出：** `requirement.json` 和 `spec.md`。

### 5. 歧义检测与澄清

**自动检查：**

- 模糊词：快速、友好、尽量、适当等是否有量化定义。
- 缺失角色、权限、异常路径、边界值和兼容要求。
- 验收条件能否转成测试。
- 需求之间是否冲突。

**状态：**

- 可自动补全的非关键细节：记录假设后继续。
- 影响业务语义、安全或数据的歧义：`NEEDS_CLARIFICATION`。

**闸门：** 所有关键需求都具备可观察的验收结果。

### 6. 生成规格差异

对存量系统，不生成孤立 PRD，而是生成“现有规格 -> 目标规格”的差异：

- 新增能力
- 修改能力
- 删除能力
- 兼容性影响

**输出：** proposal、design、tasks、spec delta。

## 阶段 2：影响、风险与计划

### 7. 建立需求追踪

为每条需求生成追踪 ID，并预留关联：

`REQ -> SPEC -> TASK -> CODE -> TEST -> BUILD -> DEPLOY -> SLO`

**闸门：** 不允许“无需求代码”，也不允许关键需求没有测试和运行指标。

### 8. 代码与系统影响分析

**自动动作：**

- 检索相关模块、API、数据库表、事件和配置。
- 分析调用图和依赖图。
- 识别跨仓库、数据迁移和兼容性影响。
- 找出相似历史变更与事故。

**输出：** `impact-analysis.json`、候选文件列表、影响图。

### 9. 威胁建模和风险评分

至少评估：

- 身份认证与授权
- 敏感数据和隐私
- 外部输入与提示注入
- 数据库迁移和数据丢失
- 公共 API/协议兼容
- 基础设施和权限扩大
- 用户规模和回滚难度

**输出：** 风险等级 `low/medium/high/critical`、必需检查、审批策略。

### 10. 生成实施计划

计划必须包含：

- 技术方案与取舍
- 文件/模块级改动
- 测试策略
- 数据迁移策略
- 观测与告警
- 发布与回滚

**闸门：** 计划不能只描述“写代码”，必须描述如何证明正确。

### 11. 拆分可执行任务

每个任务应：

- 可在一个隔离上下文内完成。
- 有明确输入、输出和验收命令。
- 尽量独立，显式声明依赖。
- 限制变更范围和最大尝试次数。

**输出：** 有向无环任务图。

## 阶段 3：代理研发

### 12. 创建隔离执行环境

为每个任务创建临时分支/工作树和容器沙箱：

- 固定基础镜像与依赖锁。
- 默认无生产网络和生产凭证。
- 按白名单开放命令、目录和网络域名。
- 设置时间、Token、成本和重试预算。

### 13. 先生成或更新测试

根据验收条件生成：

- 单元测试
- 组件/集成测试
- API 契约测试
- UI E2E 测试
- 数据迁移测试
- 性能和安全测试

测试应先在旧实现上失败或明确证明新增覆盖，否则可能是无效测试。

### 14. 实现代码

代理读取规格、计划、任务和项目规则后修改代码。

**硬约束：**

- 不得修改原始需求。
- 不得删除失败测试来“修绿”。
- 不得扩大权限或关闭扫描。
- 不得提交密钥、生成物或无关重构。

### 15. 本地自验证循环

执行：

`format -> lint -> typecheck -> focused tests -> full tests -> build -> security scan`

失败时根据错误证据修复，直到：

- 全部通过；
- 达到尝试/成本上限；
- 判断规格或环境存在阻塞。

每轮必须保存真实命令、退出码和日志引用。

### 16. 独立审查

使用独立上下文检查：

- 需求覆盖
- 正确性和边界条件
- 安全与权限
- 并发、事务和资源泄漏
- 兼容性
- 测试缺口

审查者不能只接受实现代理的总结，必须读取 diff 和证据。

## 阶段 4：PR 与确定性 CI

### 17. 创建候选 PR

PR 自动包含：

- 需求和规格链接
- 变更摘要
- 风险等级
- 测试证据
- 数据迁移与回滚
- 观测指标
- AI 参与和人工修改记录

### 18. 执行 PR 闸门

建议顺序：

1. 格式、lint、类型检查
2. 单元、集成、契约、E2E
3. 需求追踪完整性
4. SAST、依赖、Secret、许可证扫描
5. IaC 和策略检查
6. 覆盖率与变更覆盖率
7. 性能预算
8. 临时预览环境和冒烟测试

任何阻断失败都回到代理修复循环；环境故障与代码故障分开统计。

### 19. 合并决策

由风险策略决定：

- 低风险 + 全部闸门通过 + 变更范围受限：可自动合并。
- 中风险：CODEOWNERS 审批。
- 高/关键风险：领域、安全和发布责任人审批。

合并使用受保护分支，禁止绕过必需检查。

## 阶段 5：构建与发布

### 20. 构建不可变制品

从受保护分支构建一次：

- 应用包或容器镜像
- SBOM
- 漏洞与许可证报告
- 测试报告
- 签名和 provenance

用 digest 标识，禁止用可移动标签作为唯一发布身份。

### 21. 部署开发和预发布环境

CI 更新环境配置仓库中的制品 digest，Argo CD 收敛环境。

自动验证：

- 部署健康
- 数据库迁移
- API/UI 冒烟
- 契约兼容
- SLO 基线对比

失败后回滚 Git 中的目标版本或执行预定义修复动作。

### 22. 渐进式生产发布

建议流量阶段：

`0% -> 1% -> 5% -> 25% -> 50% -> 100%`

每阶段检查：

- 错误率
- 延迟分位数
- 饱和度
- 关键业务指标
- 新旧版本差异

达到失败阈值立即暂停并自动回滚；指标不可用时默认失败关闭。

### 23. 发布后验证

完成 100% 流量不代表结束。继续观察一个稳定窗口：

- 合成探测
- 核心用户旅程
- 数据完整性
- 异步任务积压
- 成本异常
- 用户反馈和告警

通过后标记 `VERIFIED`，否则进入 `ROLLED_BACK` 或 `INCIDENT`。

## 阶段 6：闭环

### 24. 证据归档与反馈

归档完整链路：

- 原始需求哈希
- 最终规格和决策
- 代码提交和 PR
- 测试、扫描、审批
- 制品摘要、SBOM、签名、provenance
- 环境和发布记录
- SLO 结果、回滚和事故

自动更新：

- 需求状态和变更日志
- 服务目录和运行手册
- DORA 指标
- 失败模式知识库
- 后续修复需求

## 推荐状态机

```text
RECEIVED
  -> NORMALIZED
  -> NEEDS_CLARIFICATION | SPEC_READY
  -> PLANNED
  -> IMPLEMENTING
  -> VALIDATING
  -> PR_OPEN
  -> CI_FAILED | MERGE_READY
  -> MERGED
  -> ARTIFACT_READY
  -> STAGING
  -> RELEASE_READY
  -> CANARY
  -> PRODUCTION
  -> VERIFIED

任意发布状态 -> PAUSED | ROLLED_BACK | INCIDENT
任意执行状态 -> BLOCKED | CANCELLED
```

状态转换只能由带证据的事件触发，不能由模型自由修改最终状态。
