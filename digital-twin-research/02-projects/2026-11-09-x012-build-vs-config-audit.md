# X-012 构建、配置与开源底座审计

日期：2026-11-09
访问日期：2026-11-09
状态：公开资料审计完成；实际试用待 X-012A/B 均通过后执行

## 结论

X-012 不能直接在现有专家分身平台内完成干净的 2×2 因果实验，但这不构成新产品机会。

当前最小正确路径是：

1. 使用现有随机化脚本、PostgreSQL、统一模型调用、Stripe 和一个薄 Web 壳执行实验。
2. 商业专家分身平台只作为实验通过后的生产替代，不作为 X-012 的主运行时。
3. 不训练三个独立“分身”，不为四组创建不同知识库，也不建设通用数字分身平台。
4. 只有 X-012A/B 均证明付费、留存和跨专家价值后，才启动 X-013，实际核验 Delphi、Coachvox、BuddyPro 和开源组合能否低成本复制结果。

公开资料已证明“专家知识代理 + 白标 + 收费”高度商品化。尚未被公开证明的是：同一知识快照、同一输出、参与者级分层随机、身份显隐、本人盲审和真实支付能否在一个现有平台中同时成立。

“公开资料未发现”只记为 `未知`，不记为产品缺口。缺口必须通过实际试用、导出记录和配置成本证明。

## X-012 必需能力

| 能力 | 必须满足的实验约束 |
| --- | --- |
| 同一知识快照 | A/B/C/D 使用完全相同的授权资料、版本和检索结果 |
| 分层随机 | 按专家、既往关系、近期需求和渠道做参与者级区组随机 |
| 身份显隐 | 只改变专家姓名与授权身份展示，不改变内容质量或模型 |
| 真人签认 | C/D 由同一专家按同一 rubric 复核 |
| 复核盲法 | 专家看不到组别、既往关系、支付状态和是否展示姓名 |
| 真实支付 | 四组同价，保留支付成功、失败、退款和争议事件 |
| 事件导出 | 可导出报价、曝光、支付、问题、回复、复核、退款和成本 |
| 结果隔离 | 专家与运营人员在实验结束前看不到分组转化 |
| 删除与撤回 | 资料、参与者输入和未进入法定留存的数据可删除 |

### Delphi

官方 [API 文档](https://docs.delphi.ai/api-immortal-only.md) 显示 API 可创建对话、管理受众、搜索知识和读取用量，但 API 只在高阶方案开放。官方文档问答进一步确认：

- 没有文档化的逐条专家审核门禁；如需审核，必须在自有应用中先截留答案再送审。
- 一个 Delphi 可提供同一知识，但 owner identity 保持不变；随机分配和显示层匿名要由自有应用完成。
- 没有文档化的终端用户原生结账、订阅或退款；真实支付需外接。

因此，Delphi 能替代知识摄取和回答生成，不能替代 X-012 的实验控制。若已经需要自建路由、支付、盲审和数据层，X-012 阶段使用高价 API 不会减少核心风险。

### Coachvox

[官方产品页](https://coachvox.ai/) 明确提供专家资料训练、分享页、嵌入、客户会话和 Zapier 集成。[官方收费文档](https://support.coachvox.ai/article/96-faqs-charging-for-access) 明确支持 Stripe Connect、订阅、多价格、优惠券和付费访问。

但公开文档同时显示：

- 外部会员登录不能与 Coachvox 登录同步。
- 收费产品在注册时由用户选择，不是研究方预先锁定的分层随机组。
- 未发现同一知识库按参与者切换 named/anonymous 身份的公开能力。
- 未发现答案发布前由本人盲审并保存签认差异的公开能力。

Coachvox 可以证明“专家 AI 可以收费”，不能直接证明 X-012 的因果链。

### BuddyPro

[官方产品页](https://buddypro.ai/) 声明提供白标专家分身、长期记忆、Stripe 支付和订阅管理。收入、日活、客户数和投资回报均为厂商自报，只能作为供给和商业模型线索。

公开页面未证明参与者级随机、匿名身份组、逐条本人签认或盲审。它应在 X-013 中通过实际演示核验，不能因白标和收费能力直接判定为可执行 X-012。

### 为什么不让 GrowthBook 负责正式随机

GrowthBook 适合在线实验和变体交付，也支持服务端评估与稳定分桶。但 X-012 已预注册：

- 每名专家固定 80 人。
- 确认性主样本只包含 `aware_nonbuyer / unaware_adjacent_buyer`，每名专家固定为 40/40；`prior_buyer` 仅可进入独立探索队列。
- 每个区组内按参与者分配 A/B/C/D。

现有 [随机化脚本](../scripts/x012-randomize.mjs) 已对正式 240 人做精确区组分配并拒绝不完整输入。它比在线百分比分流更符合预注册。GrowthBook 最多读取已生成的 arm 并交付页面，不得重新分配。

### 为什么不直接使用 Second Me

Second Me 的价值是把记忆和身份训练在一起；X-012 刻意要求把身份展示与知识内容分开。若 named 与 anonymous 组由不同身份模型生成，输出差异会混入模型、记忆和提示差异，无法识别姓名本身的效应。

因此，X-012 的四组必须调用同一个知识快照和同一个生成路径。专家姓名只在展示层变化，签认只在发布门禁变化。

## 一次性实验壳

这不是产品架构，只是可删除的验证设施。

| 层 | 最小实现 | 约束 |
| --- | --- | --- |
| 资格与分配 | 现有 CSV 模板、`x012-randomize.mjs`、PostgreSQL | arm 只在服务端保存 |
| 报价与支付 | 一个中性 Stripe Checkout 产品、相同价格 | 发票、URL 和产品名不泄漏专家身份 |
| 知识 | 单一授权快照；优先 PostgreSQL + pgvector，必要时 RAGFlow | 四组共享相同 chunk、版本和检索配置 |
| 生成 | 同一模型、系统提示、温度、响应预算 | named/anonymous 不改生成内容 |
| 展示 | 服务端按 arm 决定身份文案 | 客户端不得拿到其他变体 |
| 复核 | 独立 reviewer queue | 只显示输入、草稿、来源和 rubric，不显示 arm、关系或支付 |
| 签认 | 保存原稿、修改 diff、复核人、时间和 rubric 结果 | C/D 同一专家、同一时限 |
| 观测 | Langfuse + 不可变事件表 | 记录调用、来源、成本、错误和版本 |
| 退款 | Stripe Refund API 与 Webhook | 处理重复、乱序、失败和签名验证 |

为保证四组服务水平一致，A/B 也应在预设时间窗发布，不能因为没有人工复核而系统性更快。C/D 的专家只看到待复核队列，不能访问转化看板。

## 构建与配置决策

### X-012 阶段

允许构建：

- 资格、分配、支付、提交、统一回答、盲审和事件导出的薄实验壳。
- 只支持三个已定义输入边界和最多 240 名参与者。
- 实验结束后可删除，不承诺多租户、市场、增长、Avatar 或自主行动。

禁止构建：

- 通用专家创建器。
- 专家市场或订阅平台。
- 长期人格训练、语音或视频形象。
- 多 Agent 自主执行。
- 在 X-012 结果前包装任何产品品牌。

### X-012A/B 均通过后

默认顺序：

1. 配置 Delphi、Coachvox、BuddyPro 或开源组合。
2. 执行统一的 X-013 测试，记录实际配置时间、首年成本和不可满足项。
3. 若任一方案在 20 个工程人日内、首年软件成本不超过 10,000 美元，并满足全部强制门禁，则使用现有平台，不建设独立 SaaS。
4. 只有现有方案失败，并获得 3 个带预算和日期的书面信号或 1 个付费试点，才允许定义产品。

20 人日和 10,000 美元是“技术差异是否足以支持新产品”的否决线，不是市场定价。阈值在 X-013 启动前冻结，不得因偏好自建而事后降低。

## 可能的产品形态

只有 X-012A、X-012B 和 X-013 均通过后，仍可能成立的不是又一个“专家聊天分身”，而是现有专家代理之上的 **Expert Assurance Layer（专家保证层）**：

- 固定并版本化授权知识快照。
- 对高价值答案执行同一专家盲审。
- 保存来源、原稿、修改 diff、签认和撤回记录。
- 将身份展示、签认责任和生成质量作为独立变量治理。
- 可覆盖多个现有专家分身平台，而不重新建设知识聊天和支付市场。

该形态仍只是条件假设。若用户只为身份付费，现有白标平台已足够；若只为签认付费，应转向专家验证工作流，不再使用数字分身定位。

## 证据边界

- 本轮只核验公开页面、官方文档和开源仓库，不包含付费账户内的真实配置。
- Coachvox 和 BuddyPro 的客户收入、留存、日活及投资回报是厂商声明。
- GitHub Star、更新时间和许可证不能证明可用性、正确性或合规性。
- 平台未公开某能力不等于没有该能力；X-013 必须通过实际演示或试用判定。
