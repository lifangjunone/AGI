# 数字分身业务逻辑 v1

> 状态：业务重构草案
> 目的：在继续做页面和后端之前，先定义可收费、可验证、可治理的业务闭环。
> 当前结论：旧版“个人 AI 接待页”只能作为一个渠道适配器，不能作为产品本体。

## 0. 先纠正产品定义

“上传文章，生成一个像你的 AI 分身”不是一个完整业务。它只有输入，没有结果责任：

- 用户不知道为什么要持续维护；
- 访客聊天不等于产生收入；
- “像不像”不是足够强的付费理由；
- 资料越多不代表能力越强；
- 分身无法判断什么时候应该回答、什么时候必须停止；
- 产品方无法证明一次回答为客户创造了什么价值。

新的定义应该是：

> 在明确授权和边界内，把一个专家反复完成的高价值工作，变成可调用、可验证、可追责的数字工作能力。

数字分身是能力的一个交互入口，不是产品本身。

```text
真实工作
  → 证据与判断链
  → 能力候选
  → 试岗验证
  → 限定范围上线
  → 真实结果对照
  → 升级、限制或失效
```

## 1. 先选一条能收费的业务链

第一版不要同时做“创始人、专家、老师、IP、客服、销售”。这些角色的价值单位、风险边界和购买人完全不同。

### 推荐第一条业务链：专家/顾问的咨询前筛选与交付准备

这里的产品不是“替专家聊天”，而是：

> 在一次高价值咨询发生前，完成资格筛选、背景收集、问题澄清和材料准备；把合格线索变成专家可以直接处理的咨询简报。

为什么先选它：

1. 结果边界相对清楚：筛选、收集、摘要，不替专家做最终承诺。
2. 价值可以度量：有效预约率、专家节省时间、取消率、线索到成交率。
3. 允许人工确认：早期不需要声称完全自动。
4. 公开接待页是合理入口，但不再是最终产品。
5. 后续可以扩展到售前诊断、课程咨询、招聘初筛等相邻流程。

### 不选的方向

| 方向 | 现在不选的原因 |
| --- | --- |
| “像本人”社交分身 | 难以证明付费价值，容易陷入人格娱乐 |
| 全自动顾问 | 责任和事实准确性不足，无法确定风险 |
| 视频数字人 | 解决的是表现层，不是业务价值 |
| 泛客服/泛销售 | 已有成熟产品，切入点不够窄 |
| 企业员工能力复制 | 长期价值更大，但需要权限、证据、组织治理，作为第二阶段 |

## 2. 用户、买方与责任人

不能把“专家”和“访客”混为一个用户。

| 角色 | 得到什么 | 付出什么 | 最怕什么 |
| --- | --- | --- | --- |
| 专家/顾问（能力所有者） | 少做重复沟通，获得更完整的咨询简报 | 确认边界、处理高价值例外 | 分身乱承诺、损害声誉 |
| 业务负责人/工作室主理人（买方） | 提高有效咨询产能和转化 | 付费、配置流程、验收结果 | 买到一个漂亮聊天机器人 |
| 访客/潜在线索（服务对象） | 更快判断是否适合咨询，减少来回沟通 | 提供项目背景和联系方式 | 被误导、隐私泄漏、被强推销售 |
| 运营/助理（执行者） | 统一处理线索、跟进和预约 | 维护规则、处理异常 | 信息散落、无法追溯 |

第一版的付费人应该是“有稳定咨询收入、但被低质量咨询请求打断的专家/顾问或小型工作室”，而不是普通个人用户。

## 3. 价值承诺与收费单位

### 对买方的承诺

不是“生成一个分身”，而是：

> 用一个可控的 AI 接待流程，把每个新咨询请求整理成“是否值得本人处理”的判断材料，减少无效沟通，并提高有效预约的准备度。

### 北极星指标

```text
每周被专家确认“值得处理”，且带有完整背景和明确问题的有效咨询简报数
```

不能用以下指标替代价值：

- 对话轮数；
- 上传资料数量；
- 生成的 Persona 字数；
- 模型回答相似度；
- 创建了多少分身。

### 建议收费逻辑

首版采用“基础订阅 + 有效简报额度”，不要按聊天 token 或头像时长收费。

```text
月度工作区订阅
  + 每月包含一定数量的有效咨询简报
  + 超额按“专家确认进入处理”的简报计费
```

收费事件必须发生在业务价值已经被确认之后：

```text
访客完成必要信息
→ 规则判断通过
→ 生成简报
→ 专家确认进入处理
```

仅仅发生了一次聊天不能算付费事件。被拒答、垃圾请求、重复请求和未完成资料收集不计费。

## 4. 完整业务状态机

### 4.1 访客请求状态

```text
arrived
  → disclosed
  → collecting_context
  → qualifying
      ├─ insufficient_information → needs_more_context
      ├─ out_of_scope             → declined
      ├─ high_risk                → human_review
      └─ fit                      → brief_ready
  → owner_review
      ├─ accept                   → scheduling
      ├─ ask_follow_up            → needs_more_context
      └─ decline                  → declined
  → scheduled
  → completed / cancelled / no_show
```

每一个状态必须记录进入原因、规则版本、引用证据和操作者。不能只保存当前状态。

### 4.2 AI 分身在每一轮必须做的判断

```text
身份声明
→ 意图识别
→ 是否需要补充背景
→ 是否命中服务范围
→ 是否涉及不可代替本人确认的事项
→ 是否有足够证据回答
→ 选择动作：回答 / 追问 / 生成简报 / 转本人 / 拒答
```

回答文本只是最终产物，真正的业务状态是上面这组决策。

## 5. “分身能做什么”必须写成动作权限

### 允许自动完成

- 说明专家公开身份和服务范围；
- 解释已经确认的公开内容；
- 收集项目阶段、目标用户、当前问题和期望结果；
- 提示访客准备必要材料；
- 识别缺失字段并追问；
- 生成结构化咨询简报；
- 提供公开预约入口；
- 对重复请求去重。

### 只能给建议，不能直接执行

- 判断访客是否大概率适合预约；
- 对访客问题做初步分类；
- 建议下一步需要准备什么；
- 建议专家是否值得处理；
- 从公开资料中给出非承诺性观点。

### 必须转本人确认

- 报价、折扣、付款、合同；
- 合作、投资、录用、资源引荐；
- 具体项目方案或结果承诺；
- 私人联系方式；
- 任何涉及第三方隐私或未公开资料的请求；
- 访客声称存在紧急损失、法律或安全责任的请求。

### 必须拒绝

- 冒充本人或隐瞒 AI 身份；
- 要求伪造专家观点、聊天记录或证明；
- 试图绕过权限获取私密资料；
- 把未验证信息包装成专家承诺。

## 6. 证据和资料逻辑

“上传资料”不是业务模型。资料必须有用途、权限和验证状态。

### 四层数据

```text
原始证据层
  文章、访谈、FAQ、服务说明、历史咨询记录

结构化事实层
  身份、服务范围、案例、公开观点、禁区、预约规则

业务规则层
  触发条件、追问顺序、资格判断、转人工条件、拒答规则

结果证据层
  简报是否被采用、预约是否发生、咨询是否完成、是否需要返工
```

### 每条可用于回答的内容必须带

- 来源；
- 来源权限；
- 更新时间；
- 是否公开；
- 适用场景；
- 是否允许直接回答；
- 是否需要本人确认；
- 被纠正的历史记录；
- 失效时间或复核条件。

没有来源或已经被撤回的内容，不能进入自动回答路径。

## 7. 咨询简报的业务结构

简报不是聊天记录摘要，而是专家下一步可以直接使用的工作输入。

```text
访客身份
项目/业务
当前阶段
目标用户
当前问题
已经尝试过什么
已有证据
希望本次咨询得到什么
适合由专家判断的 1-3 个问题
AI 分身未能确认的内容
风险和边界提醒
来源引用
```

### 简报合格门槛

以下字段不完整时，只能保持 `needs_more_context`，不能进入“有效简报”计费：

- 访客在做什么；
- 目前卡在哪里；
- 希望得到什么结果；
- 至少一个可验证背景或已有尝试；
- 访客明确知道这是 AI 接待分身。

## 8. 业务规则版本化

任何影响“回答、追问、转人工、收费”的规则都要版本化。

```text
SourceVersion
  → FactVersion
  → PolicyVersion
  → QualificationDecision
  → BriefVersion
  → OwnerDecision
```

当专家修改服务范围或边界时：

1. 新请求使用新规则；
2. 旧简报保留当时使用的规则版本；
3. 已发布页面显示当前版本；
4. 受到规则变化影响但尚未处理的线索进入复核；
5. 不允许静默覆盖历史判断。

## 9. 最小可行产品真正应该做什么

### P0：一条业务链

只做以下完整闭环：

1. 专家配置服务范围、适合对象、禁区和预约规则；
2. 导入公开资料和 5-10 条本人确认的历史问答；
3. 发布一个公开接待入口；
4. 访客完成最少信息收集；
5. 系统生成结构化咨询简报；
6. 专家在收件箱中接受、补问或拒绝；
7. 系统记录结果并给出有效简报率、预约率、补问率和拒绝原因。

### P0 明确不做

- 不做声音、视频和数字人形象；
- 不做“像本人”的抽象分数；
- 不做无限自由聊天；
- 不做自动报价、自动承诺；
- 不做复杂知识库管理中心；
- 不做泛 Agent 市场；
- 不做企业员工全量工作旁听；
- 不做模型训练/微调承诺。

## 10. 成功判定

用一个真实专家跑 2 周，至少满足：

| 指标 | 目标 |
| --- | --- |
| 访客完成必要信息比例 | ≥ 60% |
| 生成简报被专家认为“可直接处理” | ≥ 70% |
| 专家平均每条简报修改时间 | ≤ 2 分钟 |
| 无效/垃圾请求被拦截比例 | ≥ 50% |
| 有效简报到预约转化 | 比人工基线提升，或保持不下降 |
| AI 越权承诺 | 0 次 |
| 专家愿意继续使用 | 连续两周主动打开并处理 |

如果不能证明上述结果，就不应该继续扩展到声音、视频或“人格训练”。

## 11. 第二阶段：从接待分身升级到能力分身

只有 P0 证明专家接待链成立后，才进入更强的“能力分身”：

```text
真实咨询记录
→ 判断—证据—行动—结果链
→ 经验卡片
→ 试岗案例
→ 影子咨询
→ 人工验收
→ 限定能力授权
```

这一步吸收已有数字员工研究中的原则：

- 不把资料数量当作能力；
- 不把模型会回答当作已经学会；
- 经验必须有证据和结果；
- 先影子工作，再建议工作，最后才是受控执行；
- 高风险动作永远保留本人确认。

## 12. 对当前代码的结论

当前代码中的 `/studio`、`/twin/li-ming` 和 `/studio/inbox` 可以保留为视觉和交互实验，但不能继续当作产品本体。

下一次实现应优先重构：

1. `Twin` → `ExpertWorkspace / ReceptionPolicy / Lead / Brief / OwnerDecision`；
2. 把状态机和规则判断放进 `src/lib/domain`，不放在页面组件里；
3. 把 mock 对话改成基于业务状态的事件流；
4. 把“发布”定义成发布一版接待规则，而不是跳转到公开页；
5. 把收件箱改成简报和决策处理，不再只是展示卡片；
6. 为每次回答保存规则版本、引用来源、风险分类和下一动作。
